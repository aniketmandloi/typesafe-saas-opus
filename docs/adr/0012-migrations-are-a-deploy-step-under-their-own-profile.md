# Migrations are a deploy step under their own deployment profile

Migrations run as a **one-shot job before a new revision serves traffic**, never at application boot. The runner is a fourth entrypoint in `apps/server` (`src/entrypoints/migrate.ts`), and it composes the **`migrate` deployment profile** — the only profile requiring the direct, non-pooled connection string, and the only one composing **no adapters at all**.

Boot-time migration was rejected because two of the kit's three targets make it unsafe by construction: on Lambda and Vercel, N cold starts race the same migration with no coordination, and [ADR-0010](./0010-dev-runs-raw-source-on-bare-node.md)'s dev loop restarts constantly besides. One process, one lock, one time is the only shape that holds across containers, Lambda and Vercel.

**A profile composing zero adapters looks degenerate, and is the point.** [#15](https://github.com/aniketmandloi/typesafe-saas-opus/issues/15) made the deployment profile the composition unit precisely so that a deployment requires exactly its providers' variables. The migrator needs no storage, no email and no queue, so sharing `apps/server`'s profile would make a migration job demand S3 and SES credentials it will never use. Its env contract is the shortest in the kit: the direct URL and nothing else. That also keeps the direct URL out of the server's schema, so a leaked server environment cannot bypass the pooler.

The entrypoint/profile split is the same one the worker already demonstrates ([ADR-0021](./0021-the-worker-is-an-entrypoint-not-an-app.md)). The worker is *different entrypoint, same profile*; the migrator is *different entrypoint, different profile*. Those axes being independent is what [#15](https://github.com/aniketmandloi/typesafe-saas-opus/issues/15) established when it made the profile the composition unit rather than the target. A separate `apps/migrate` would duplicate build configuration for one file and is not a separate product surface.

## Consequences

**Migrations are committed SQL, generated by `drizzle-kit generate`. `push` is not used anywhere, including dev.** `push` diffs against a live database and applies silently, which makes it unreviewable and — more importantly — means it would happily drop the append-only trigger it knows nothing about. A dev shortcut that diverges from the deploy path is how that trigger goes missing in production only.

**[ADR-0008](./0008-audit-events-written-by-use-cases.md)'s append-only trigger rides as a custom migration.** `drizzle-kit generate --custom` emits an empty SQL file registered in `meta/_journal.json`, so it orders with every other migration and is reviewable in a pull request. It is guarded by an integration test that asserts **behaviour, not existence**: the test issues a real `DELETE` and a real out-of-band `UPDATE` against `audit_event` and requires both to be rejected. Asserting `pg_trigger` membership would pass for a trigger that exists but was rewritten wrongly.

**The migrator holds a Postgres advisory lock for the duration of `migrate()`.** Drizzle's Postgres migrator has **no locking**: it reads the latest row from `__drizzle_migrations`, then applies every pending migration inside one transaction. That transaction gives atomicity, not mutual exclusion, so two concurrent runners read the same watermark and both apply. Serialising in the deploy pipeline is not a promise the kit can make, since it does not own the cloner's CI and rollbacks are exactly when two deploys overlap. With the lock, the second runner blocks and then finds nothing pending. There is no pooler interaction to worry about — the pinning hazard advisory locks carry under RDS Proxy cannot arise, because this connection is the direct one by construction.

**The migrate profile depends on `pg-boss`, and composes no adapter to get it.** [ADR-0021](./0021-the-worker-is-an-entrypoint-not-an-app.md) runs every target with `migrate: false`, so pg-boss's own schema is installed here, beside Drizzle's. That makes a pg-boss version bump a migration like any other, which is the point — the alternative puts a schema check on every cold start and a locked migration inside a Vercel cron invocation. It does not make the queue an adapter of this profile: the migrator installs the schema and never enqueues or drains, so the zero-adapter claim above still holds.

**Seeding is opt-in (`pnpm db:seed`) and no test depends on it.** A clean checkout gets an empty migrated database. Auto-seeding teaches cloners to build on rows they did not create, and the seed then becomes a fixture nobody dares delete. Tests create their own data, which they need anyway for the org-A-cannot-read-org-B assertion [ADR-0001](./0001-application-level-tenant-scoping.md) depends on.
