# Background jobs are a queue seam, backed by pg-boss and SQS

Deferred work sits behind one kit-owned queue interface with two drivers: **pg-boss in process** as the default, and **SQS plus Lambda** for the AWS reference deployment. Durable multi-step execution engines — Inngest, Trigger.dev — are excluded from the seam and from the kit.

**Control inversion is a wiring concern, which is why SQS fits.** A handler written as `(payload, ctx) => Promise<void>` is callable from a pg-boss `work()` loop, a Graphile task, a BullMQ processor, *and* a generated Lambda `SQSHandler` shim that parses `event.Records`, validates, calls the handler and returns `batchItemFailures`. It is the same move the kit already makes with Hono: tRPC turns the HTTP framework into a thin mount point, so who invokes the handler stops being the handler's business.

**What does not fit is durable execution**, and not because those providers are hosted or own the runtime. Their unit of work is a **checkpointed resumable run**; every queue's is a **job**. A function using `step.run()` / `step.sleep('3 days')` / `step.waitForEvent()` is re-entrant and replayed from the top on every step, with prior results memoized; run the same function under pg-boss and it executes once top to bottom with a literal three-day timer inside a job lock. Different program. That leaves two bad options: keep the interface at `(payload, ctx) => Promise<void>` and pay per-execution pricing for durability the kit has forbidden itself from using — *this* is the lowest-common-denominator collapse, and it lands on the hosted providers rather than on SQS — or expose steps and then implement a durable execution engine on Postgres and SQS to make the other drivers conform, which is a project the size of Inngest, not an adapter. Trigger.dev fails even the first: its tasks are built into container images by its own CLI and deployed to its infrastructure, so the handler is a deployment artifact rather than a callback, and an adapter would be a code generator with a second deploy pipeline.

**The single declaration is `@repo/jobs`'s `jobPayloads` record**, not a driver's generics. pg-boss and BullMQ take per-call-site generics defaulting to `object`/`any` — the hand-maintained second declaration of one shape that the kit's typesafety contract calls a bug. Graphile's `GraphileWorker.Tasks` global augmentation is a genuine central registry and the best of the queues, but it is type-only and its own docs warn that a SQL-side `add_job()` bypasses it; SQS has no typing at all. Because the kit must own that registry anyway, typing never differentiated the candidates: `parseJobPayload` validates at the seam **in both directions** — on enqueue so a malformed payload never reaches the queue, on dequeue because a payload may have been written by an older deployment — which closes Graphile's SQL hole and SQS's total absence with one mechanism.

## Considered options

**Graphile Worker** loses on three concrete gaps, none of them about typing: no dead-letter facility at all, where pg-boss has `deadLetter` plus `redrive()`; no dashboard, where pg-boss ships an official MIT `@pg-boss/dashboard` — a starter kit should not hand a cloner a set of admin SQL functions and an instruction to build a UI; and [UTC-only cron](https://worker.graphile.org/docs/cron), where pg-boss does timezone and RRULE schedules with a catch-up policy, which any SaaS sending a "9am local" digest walks straight into. Its fixed, non-configurable `exp(least(10, attempt))` backoff is a smaller third strike.

**BullMQ v6 is rejected reluctantly, and on age rather than architecture.** It shipped an in-core PostgreSQL backend on 2026-07-30 — the same `Queue`/`Worker`/`FlowProducer`/scheduler/rate-limiting API selected by passing `createPostgresBackend`, with documented feature parity and the vendor maintaining the conformance tests. That is strictly the better shape for this kit: one library spanning Postgres at the floor and Redis at scale, instead of a driver per backend written here. It was seven weeks old when this was decided, BullMQ's own docs still name Redis "the default and the most battle-tested option", and schema downgrades are unsupported. A fork-and-go kit inherits its defaults into every cloned project, which is the wrong place for a new datastore bet. Revisit in about a year: BullMQ's processor signature already matches the handler contract, so adopting it means writing one driver, not rewriting jobs.

## Consequences

**Cron, dead-lettering and concurrency are absent from the interface**, which reads like an omission and is not. Each is a deploy-time declaration in a different place — pg-boss's scheduler needs a running worker, SQS wants EventBridge Scheduler and a redrive policy as Terraform resources, concurrency is a per-process integer here and an event-source-mapping poller count there — so folding them in would shape the interface around one driver's capabilities. The portable contract for failure is "terminal failure is observable and replayable", not a shared DLQ API.

**`runAt` is capped by SQS's 15-minute delay quota**, the one hard limit a portable delay cannot honour. Anything longer is a scheduled sweep, which is how [ADR-0007](./0007-organization-soft-delete-and-purge.md)'s 30-day purge window is served.

**There is no transactional enqueue, and `JobContext` carries no transaction handle.** pg-boss can join the caller's transaction and SQS cannot, so the seam takes the weaker guarantee and use cases enqueue *after* commit. That is a choice of which failure a crash produces: an invitation with no mail sent, which a re-invite repairs, rather than a mail linking to an invitation that was rolled back, which nothing repairs. There is no cancellation signal either — a draining pg-boss worker and a frozen Lambda are not the same event, and a handler reacting to one is coupled to a driver's lifecycle.

**Vercel has no worker process.** Fluid compute allows a cron-triggered bounded drain endpoint (300 s, 800 s on Pro), but Vercel Hobby crons fire once a day with ±59 minutes of jitter and more frequent expressions *fail at deploy*, so Hobby has no background processing worth the name; on Pro the latency floor is the cron period, and pg-boss's schedules would have to migrate into `vercel.json`, breaking the single-declaration rule. Vercel stays a supported target for the web app; background work wants a worker container or the SQS driver, and the drain endpoint is a documented degraded mode. Where the worker actually runs per target is not decided here.

**`@repo/jobs` is `universal`** — it holds payload types and the handler contract so a client can enqueue with a typed payload — while the `server`-tagged handler implementations live elsewhere. That is also why the seam names no `AbortSignal`: it lives in the DOM lib, and reaching for it would pull a platform assumption into a package that ships to a phone.

**Durable multi-step execution is out of scope for the kit**, not merely unimplemented. It is a later bolt-on, and adding it means choosing an engine, not adding a driver.
