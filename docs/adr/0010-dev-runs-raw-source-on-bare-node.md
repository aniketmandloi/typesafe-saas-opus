# Dev runs the raw source on bare Node

Local development runs `node --watch` directly on the workspace TypeScript for every `server`-tagged entrypoint — `apps/server` and the worker — with no bundler, no loader and no build step. Apps that ship through their own bundler in production keep it in development: `apps/web` and the Admin app run Turbopack, `apps/mobile` runs Metro. Relative imports carry an explicit `.ts` extension **everywhere in the repo**, uniformly, not only where Node requires it.

The premise this overturns is [Toolchain baseline](https://github.com/aniketmandloi/typesafe-saas-opus/issues/8)'s: `moduleResolution: "bundler"` was adopted repo-wide and mitigated by **running dev through a bundler too, so that dev and production resolve identically**. That mitigation is void, and the reason lives in a different decision — [Bundling a pnpm-workspace server per target](https://github.com/aniketmandloi/typesafe-saas-opus/issues/14) found there is no single production module reality to match. Container and Lambda run **one esbuild bundle**; `@vercel/node` **does not bundle at all**, tracing with nft and transpiling each file in a `readFile` hook. A dev loop can match one or the other, never both, so the bundler dev loop was buying a guarantee that does not exist.

Given that, the choice is which way the strictness should point, and it should point at **dev being stricter than production**. Bare Node resolves like Node: a bundler-only import — an extensionless relative specifier, say — fails the moment it is written rather than passing dev and failing on some future target. `moduleResolution: "bundler"` becomes self-policing, and the dev build step and its configuration leave a kit whose pitch is that a cloner can read it.

## Considered options

**A bundler in watch mode** is the incumbent and is perfectly usable: esbuild rebuilds incrementally in 124 ms against bare Node's ~410 ms edit-to-ready, and both disappear into the noise of a page reload. Performance was never the question. What it offers is parity with the *bundled* production path, at the price of a build step, a watch configuration, and a class of resolution bug that stays invisible until a target's bundler disagrees. With parity unavailable in principle, the price no longer buys anything.

**Confining the `.ts` specifier style to `server`-tagged packages** was rejected. It cannot work: bare Node loads the universal packages too — `@repo/schema`, `@repo/core`, `@repo/env`, `@repo/jobs` — so their internals need the extension regardless, and those same files are consumed by Metro and Turbopack. Splitting the style by platform tag would leave a rule every cloner must learn, that no tool enforces, at a boundary that does not align with anything else in the kit. One uniform style is greppable and boring.

## Consequences

**Explicit `.ts` extensions are a repo-wide invariant**, with `allowImportingTsExtensions: true` — legal because nothing emits. **Both bundlers accept the style**, verified by [#20](https://github.com/aniketmandloi/typesafe-saas-opus/issues/20) against running builds on branch `spike/ts-specifiers`: Next 16.3.5 under Turbopack and Expo SDK 57 under Metro both resolve `./foo.ts` and `./foo.tsx`, inside a Just-in-Time workspace package and in app code, with no resolver hook and no `transpilePackages`. In Metro this is structural rather than incidental — `resolveSourceFile` probes the verbatim specifier before it appends any `sourceExts` entry — which is the same mechanism that makes the inverse (`./foo.js` pointing at `foo.ts`) impossible.

**The exception is Metro's platform-variant lookup, which an explicit extension silently skips.** That verbatim-first probe passes no `platform`, so `./plat.ts` resolves to `plat.ts` even when `plat.android.ts` exists, while `./plat` resolves to the override. There is no error, and the dead variant still ships. The invariant is therefore stated for what actually requires it — everything bare Node loads, meaning `server`-tagged and `universal` packages — and **inside `apps/mobile` the extension is dropped wherever a platform variant exists**. This does not reopen the rejected option above: the split is app-versus-package, not platform tag, and it is enforced by lint rather than learned, because the failure is silent. The standing cost is that **a `universal` package can never carry a platform variant**, since its own internals must stay explicit for Node; nothing decided so far wants one.

**Nothing exercises the bundle until CI, so CI builds all three server artifacts on every pull request** — the esbuild bundle, the Lambda bundle and the Vercel-shaped trace. A type error is not the failure mode this guards against; an unbundleable dependency or a bundler-hostile pattern is, and with no bundler in the dev loop there is nothing else between writing it and deploying it. The builds are needed for the deploy path anyway; what changes is that they run before merge.

**`node-linker=isolated` is asserted at preinstall, not documented.** Type stripping is refused for any file whose realpath sits under `node_modules`, so `hoisted` fails with `ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING` — a message that reads like a Node bug rather than like a pnpm setting. A cloner who flips the linker to work around an unrelated dependency problem should get an error naming the cause. This was already a packaging constraint from [#14](https://github.com/aniketmandloi/typesafe-saas-opus/issues/14); it is now what the dev loop stands on.

**`pnpm dev` starts everything**: server, worker, web, Admin and the Expo dev server, which prints its QR for Expo Go rather than demanding a simulator. The worker is in the default set deliberately — a Postgres-backed queue that silently never drains is the most confusing failure this stack produces, since the mutation succeeds and the job row simply sits there. In `turbo.json` the dev tasks are `persistent`, and the Expo task additionally `interactive`, so its QR and keypress interface survive inside Turborepo's terminal UI instead of being flattened into streamed logs.

**Dev no longer matches production, and that is the point.** The residual risk runs the other way: something bare Node accepts that the production bundle rejects. That is what the three CI builds cover. The risk this removes — a bundler-only import reaching a target that cannot resolve it — was the one nobody would have caught until deploy.
